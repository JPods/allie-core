# JPods Station Template Designer Guide
**Audience:** Designers building new station templates or modifying existing ones.
**Last Updated:** 2026-06-09

---

## What a Template Is

A station template is a SketchUp component definition that represents one station
type — a traffic circle, a line-end platform, a parking station, etc. When a student
places a station in their JPods network, they are placing an instance of a template.

The template folder holds the .skp model plus a set of JSON files that describe
the template's geometry, topology, connection points, and routing behavior.
These files must stay in sync with the .skp model at all times.

---

## Files in Every Template Folder

Six files. No others are committed.

```
model.skp       — geometry source
lines.json      — topology + behavior (one source of truth)
cp.json         — CP positions (Extract Template generates)
geometry.json   — vehicle paths (Extract Template generates, Bezier-protected)
notes.md        — documents protected geometry.json tracks
image.png       — thumbnail
```

**Not committed:** `extracted.json` (internal intermediate, discarded after
Extract Template runs), `feature.json` (obsolete audit artifact), `lines~*.json`
backups, `model~.skp`, and all `model.*.json` runtime files.

---

### model.skp — The Model (You Own This)
The SketchUp model. Source of truth for all geometry. Every other file is derived
from this file or hand-authored to match it.

**Rules:**
- All guideway groups must have SketchUp Tags (Layers) matching their track names
  (e.g., `gw_platform_in`, `gw_c_0_0`, `gw_cp_in_0`). Use Entity Info to verify.
- The formation component must contain `gw_stub_pair` tagged entities marking the
  Connection Point stub positions and `dead_cap_end` tagged entities for CP tangent direction.
- Do not rename tags after cp.json is committed — the CP pipeline depends on exact names.
- Do not move a guideway group without re-running **Extract Template** (see Step 3 below).

---

### lines.json — The One Source of Truth ⚠️
**This is the most important file in the template folder.**
It contains both the physical topology and the behavioral declarations in two
clearly-owned sections. Both sections must be approved by Bill James before the
station can be built or operated.

**Why one file:** Topology and behavior are not independent. Every track name in
the behavioral chains must match a track declared in the topology. Splitting them
into two files requires permanent coordination that fails in the field. If the
behavior must be different, design a different station with different tracks.

**Section 1 — Topology (Designer owns, Noelle enforces)**
```
eps_header    — { approved_by, dt, note }
eps[]         — switch point declarations (merge, diverge, 1-1, open)
lines{}       — successor map: for each track, which tracks can follow
```
`eps_header.approved_by` locks the topology. Noelle will report defects but cannot
override a signed eps[].

**Section 2 — Behavior (Sally drafts, Bill approves, Sally executes)**
```
chains_header      — { approved_by, dt, note }
originating_chains — how pods depart by CP
landing_chains     — how pods arrive by CP
hold_loop_chain    — the holding pattern (outer ring, no platform contact)
parking_chain      — slot layout and capacity
pass_chains        — ring/circle pass-through sequences
```
`chains_header.approved_by` locks the behavior. Sally will not operate a station
whose chains are unsigned.

**Rules:**
- Edit this file when adding, removing, or renaming any track.
- Update BOTH sections when a track name changes — topology and every chain that
  references it.
- Run **Sally: Draft Chains** from the Console after topology changes to redraft
  the behavioral sections.
- After editing, run **Extract Template** then **Show Formation Tracks** to verify.
- See TFTS index (`readmes/sketchup/tfts-index.md`) under "lines.json and Topology
  Authoring" for solved problems.

---

### cp.json — Connection Point Map (Extract Template Generates)
Positions and tangent directions of all Connection Points in definition-local
coordinates. Generated by **Extract Template** in one pass alongside geometry.json.

**Do not edit manually.** If CPs look wrong, delete cp.json and re-run Extract
Template. The tool now derives tangents from the rail span geometry (exact) rather
than bounding box center (which introduces angular error on asymmetric stations).

---

### geometry.json — Vehicle Centerline Paths (Extract Template Generates) ⚠️
The vehicle path for every track: Bezier curve pts, Z corrections, arc pts.
Used by **Show Formation Tracks** and the animation system.

**This is the most sensitive generated file.** Some tracks are hand-authored and
cannot be regenerated automatically. See `notes.md` for exactly which tracks are
protected in this template.

**Rules:**
- Run **Extract Template** from the Console to generate both cp.json and geometry.json
  in one pass. There is no separate "Generate Geometry JSON" step.
- The Console will warn before overwriting protected tracks (Bezier/arc or authored=true).
- After generation, run **Show Formation Tracks** and verify every ribbon.
- Any track that shows as a straight diagonal when it should curve needs a hand-authored
  Bezier correction — see `notes.md` and `readmes/sketchup/formation-tracks-recovery.md`.
- Protected tracks have either `>2 pts_mm` or `"authored": true` — preserved automatically.

---

### image.png — Thumbnail (You Provide)
Displayed in the template picker when a student places a station. 512×512 PNG.

**To update:** take a screenshot of the model at a standard angle, crop to square,
save as image.png. No other action needed.

### notes.md — Designer Notes (You Maintain)
Documents which tracks in geometry.json are hand-authored and why — protected Bezier
curves, Z corrections, junction coordinates, and the git restore command. Written by
the session that authored the corrections; updated when the model changes.

**Read this before running Extract Template.** If it says a track is protected,
confirm the Console warning before proceeding.

## Files That Are NOT Committed

| File | Why not committed |
|------|-----------------|
| `extracted.json` | Internal intermediate — discarded after Extract Template completes |
| `feature.json` | Obsolete audit artifact from pre-lines.json era — delete if present |
| `lines~*.json` | Backup copies — archival noise; move to archive/ if needed |
| `model~.skp` | SketchUp auto-backup — never commit |
| `model.feature.json` | Runtime artifact — regenerated by Build/Validate |
| `model.followme.json` | Runtime artifact — regenerated by Build |
| `model.network.json` | Runtime artifact — regenerated by Export |
| `model.path.json` | Runtime artifact — regenerated by Build/Animate |

All `model.*.json` files are safe to delete and regenerate. They are in `.gitignore`.
committed as reference snapshots, but they are always safe to delete and regenerate.

## Building a New Template — Steps

### Step 1 — Design the model.skp

Build the station geometry in SketchUp. Rules:
- All guideway cross-sections must be the standard JPods beam profile.
- Minimum arc inside-rail radius: **1500mm** (`MIN_STATION_ARC_RADIUS_MM`).
  Use SketchUp's arc tool with a known radius; the plugin checks this at Build time.
- All arcs must be SketchUp ArcCurves (drawn with the Arc tool), not segmented polylines.
  ArcCurve extraction (Priority 1) gives exact radius and ordered pts.
- One formation component wrapping all guideways. The component origin is the station
  placement anchor point.

### Step 2 — Tag every guideway group

Open Entity Info for each guideway group and set its Tag to the track name:
- `gw_cp_in_N` — inbound CP stub (vehicle enters from outside)
- `gw_cp_out_N` — outbound CP stub (vehicle exits to outside)
- `gw_in_N` — inbound approach (ring/platform to CP junction)
- `gw_out_N` — outbound approach (CP junction to ring/platform)
- `gw_c_A_B` — ring connector arc between stations A and B
- `gw_platform_in`, `gw_lift_in`, etc. — interior station tracks

**Naming constraint for merge/diverge tracks:**
Tracks carrying inbound vehicle flow must end in `_in`.
Tracks carrying outbound vehicle flow must end in `_out`.
Ring/bypass tracks use `gw_c_X_Y` naming.
Show Formation Tracks uses these suffixes for color: `_in` = red, `_out` = blue,
`gw_c_*` = yellow. Wrong color = wrong name.

### Step 3 — Place gw_stub_pair and dead_cap_end entities

Each CP needs:
- A `gw_stub_pair` tagged edge at the stub endpoint — marks the CP position.
- A `dead_cap_end` tagged entity pointing outward from the stub — defines CP tangent
  direction. Without this, CP tangent detection falls back to geometry heuristics
  that fail on asymmetric templates (Axiom 10 — explicit datum beats derived reference).

### Step 4 — Run Extract Formation

Console → Workflow → **Extract Formation**

Generates `extracted.json` (raw endpoint geometry) and `cp.json` (CP positions and
tangents). Verify in the Console output that all expected CPs were found.

### Step 5 — Author lines.json

Copy an existing lines.json as a starting point. Define:
- `eps[]` — every switch point with `type` (merge, diverge, 1-1, open) and `in`/`out` arrays
- `lines` — successor map: for each track, which tracks can follow it
- `pass_chains` — let Sally compute from the topology (set `approved_by: ""` until verified)

This is the most design-intensive step. Draw the vehicle flow diagram first.

### Step 6 — Run Generate Geometry JSON

Console → Workflow → **Generate Geometry JSON**

Creates initial `geometry.json` from `extracted.json`. Open **Show Formation Tracks**
immediately after. Every track should draw a ribbon at the correct location.

**Common problems at this step:**
- Straight ribbon where a curve is expected → track needs a Bezier correction
- Ribbon at wrong Z → Z correction needed; set `"authored": true` after fixing
- Ribbon at large offset (thousands of mm) → coordinate frame error; check formation_xf
- Ribbon crosses the guideway at a junction → endpoint is off the arc centerline
  (for ring templates: endpoint must equal adjacent arc's FIRST or LAST pt exactly)

### Step 7 — Hand-correct geometry.json and update notes.md

For any track needing correction:
1. Edit `geometry.json` — set the correct `pts_mm` array
2. For 2-pt tracks with Z corrections, add `"authored": true`
3. Update `notes.md` — document what is protected, why, and the junction coordinates
4. Commit immediately (each correction is a separate commit)

See `readmes/sketchup/formation-tracks-recovery.md` for the Bezier formula and
worked examples for each existing template.

### Step 8 — Verify Show Formation Tracks

Open the template model → Extensions → JPods → **Show Formation Tracks**

Check:
- All inbound tracks are red, outbound are blue, ring/circle tracks are yellow
- No ribbons cross the guideway
- No straight diagonals where curves are expected
- All ribbons connect smoothly at junctions (no visible gaps)

### Step 9 — Run Build and Validate

Build constructs the 3D beam geometry. Validate (Noelle) checks:
- CP tangent directions
- Track naming and tag assignments
- Network connectivity
- Any `feature.json` defects

Fix all Noelle faults before committing.

### Step 10 — Commit the template

Commit these files:
```
model.skp
cp.json
extracted.json
geometry.json
lines.json
feature.json    (if clean — no defects)
image.png
notes.md
```

Do not commit `model.feature.json`, `model.followme.json`, `model.network.json`,
`model.path.json` as part of the template definition (these are test artifacts).

## Prohibitions

| Never do this | Why it breaks things |
|--------------|---------------------|
| Move a guideway group without re-running Extract Formation | extracted.json has stale endpoints; geometry.json silently uses wrong coordinates |
| Rename a track tag without updating lines.json | Noelle cannot find the track; routing fails silently |
| Run Generate Geometry JSON on station_thru_dip or station_line_end without reading notes.md | Destroys 3D Bezier curves and Z corrections that cannot be auto-regenerated |
| Set ring connector endpoints from switch-box geometry instead of arc FIRST/LAST pts | Ribbons cross the guideway; connector length ≠ 1000mm is the diagnostic |
| Use a segmented polyline for arcs instead of SketchUp ArcCurves | ArcCurve extraction fails; bounding-box fallback gives disconnected endpoints |
| Draw arcs below MIN_STATION_ARC_RADIUS_MM = 1500mm | Build rejects the arc and prints 🚫 |
| Edit cp.json, extracted.json, or model.*.json manually | These are generated files; manual edits will be overwritten on next generation |
| Place the formation component origin off the CP anchor | Instances place incorrectly in the network model |

## Bezier Curve Convention (Axiom 11)

When hand-authoring or correcting Bezier pts in geometry.json:

```
B1 = p0 + h * sv     sv = OUTWARD from p0 (vehicle departure direction at p0)
B2 = p3 + h * ev     ev = OUTWARD from p3 (REVERSE of vehicle arrival direction at p3)
h  = chord / 3
```

`ev` must point AWAY from p3 back toward p0. If you use the arrival direction instead
of its reverse, the Bezier will loop 180°.

For ring templates: sv at a diverge EP = CCW ring tangent; ev at a merge EP = REVERSE
of the ring departure tangent at that point.

---

## Ring Junction Rule (Axiom 21)

In any ring-topology template, every endpoint touching a ring junction must equal the
adjacent ring arc's own FIRST or LAST pt. Never use switch-box or approach-track endpoints.

**Self-check:** correct short ring connector length = **1000mm**.
If a connector is 1118mm (old wrong value), one endpoint is at a switch-box offset
~500mm inside the ring radius.

## Quick Diagnostics

| What you see | Check |
|-------------|-------|
| Red track drawn blue (or vice versa) | Tag name — does it end in `_in` or `_out`? |
| Ribbon straight diagonal | geometry.json has 2 pts; needs Bezier correction |
| Ribbon crosses guideway at junction | Endpoint off the arc centerline |
| Ribbon at wrong Z | Z correction needed; see notes.md |
| Large ribbon offset (thousands of mm) | formation_xf / coordinate frame error |
| CP not detected | Missing gw_stub_pair or dead_cap_end entity; or Tag is Layer0 |
| Noelle TAG_DEFECT | Track group Tag is Layer0 — fix in Entity Info |
| Build produces no geometry | lines.json missing or malformed |
