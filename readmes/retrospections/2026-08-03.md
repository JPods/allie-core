# Retrospection — 2026-08-03

## What Was Done
- **48,000 lines of monolith detail pages → ~2,000 lines of JSON-driven components.** ContactDetail (4,114 lines), ItemDetail (2,968 lines), CustomerDetail, VendorDetail, ManufacturerDetail, EmployeeDetail, RepDetail — all replaced by three thin orchestrators: ContactDetailJson (~220 lines), OrgDetailJson (~280 lines, serves all 5 org models), ItemDetailJson (~250 lines).
- **Communication component hierarchy built**: CommCard (110 lines) → CommList (55 lines) → CommPanel (65 lines). Replaces 1,704-line CommunicationsPanel. Reused across contact, org, and transaction detail views.
- **Product component hierarchy built**: BomCard/BomPanel, SerialCard/SerialPanel, WarehouseCard, VariantCard, XRefCard, SpecCard, ProductListPanel. Generic list panel pattern — pass model name, card component, headers.
- **OrgDetailJson serves 5 models from one component** — customer, vendor, manufacturer, employee, rep. Takes `modelName` prop, reads layout from Setting. Fetches primary contact for communications tab.
- **AdminWorkbench App/Admin toggle restored** — APP_DETAIL_COMPONENTS map with lazy imports for all JSON-driven components. Single click selects record and renders ui.json detail in right panel (App mode) or db.detail fields (Admin mode). Fixed prop mismatch: all components now accept `recordId` as universal prop. `modelName` passed from `db.selectedModel`.
- **RecordToolbar universalized** — single toolbar component for all ui.json pages (Add, Edit, Save, Cancel, Report dropdown, Model Menu with Design Layout, Delete). Used by TransactionDetail, ContactDetailJson, OrgDetailJson, ItemDetailJson.
- **useDetailLayout hook** — fetches and caches detail_layout Settings with `invalidate()` for Design Mode exit.
- **Barrel export cleanup** — removed references to archived CommunicationsPanel, CommLinkPanel, ContactPanelx2 from panels/index.ts. Inlined RefContact type into ContactPanel.tsx.
- **seed_comm_layouts management command** — seeds 19 detail_layout Settings covering comms, contact, orgs, item, serial, spec, BOM, action, document, QA, report.
- **ui-db-map.md** — complete model registry assigning every model to ui.json, ui.tsx, or db.json rendering path.
- **"Definitions first" principle established** — define name, purpose, boundaries, location, owner before building. Applied to comm components, org components, product components.

## What to Polish
- RecordToolbar button set is too wide — Delete floats far right, model menu label should be a gear icon not model name
- Dark mode styling on ContactDetailJson right panel needs review — currently rendering in light mode inside dark AdminWorkbench
- APP_DETAIL_COMPONENTS passes props that some components ignore (modeProp, dataProp, hideBreadcrumb, inline, onSaved, onCancelInline) — harmless but could be cleaner with a shared interface
- OrgDetailJson communications tab only shows when `data.contact_id` exists — should show empty state with "No primary contact" message
- Transaction detail components still need detail_layout Settings for workorder, receipt, requisition, payment

## WhatIf Bucket
- Could the APP_DETAIL_COMPONENTS map be derived from a Setting instead of hardcoded? Then adding a new ui.json model requires zero React code changes.
- What if Design Mode could export/import layout JSON as files — enabling a layout marketplace between WC3 instances?
- Should ProductListPanel support inline editing like CommCard does, or is double-click → db.detail the right pattern for all product sub-models?
- With 48K→2K proven, could the same JSON-driven pattern replace the transaction list views too? databrowser already does this — question is whether custom list views add enough value to justify their code.
