## What to Polish

- The detail toolbar `onRegisterActions` callback pattern works but the useEffect deps may cause unnecessary re-registrations — consider `useCallback` wrapping the handlers in detail components.
- The Theme selector saves to prefs but doesn't update the Redux auth state — the new theme won't reflect in `user.prefs` until next login. Could dispatch a local state update.
- Zone tooltip positioning doesn't clamp to viewport edges — tooltip can overflow off-screen near the right/bottom edge.
- The `viewPref` is called both at component level and inside the detail pane IIFE in databrowser — the IIFE call at line ~1079 is now redundant since `viewPref` is computed at top level. Clean up.
- The 16 Display pages import `{ DetailToolbar }` but don't yet check `inline` prop. Works because they're never rendered inside databrowser's APP_DETAIL_COMPONENTS, but should be added for consistency.
- DataBrowser.css has two `.db-list-pane` definitions (lines ~230 and ~271) — the first is orphaned. Clean up.

## Lessons for Allie

1. **Four toolbar layers → two** — the biggest screen space win came from recognizing that list and detail controls were in separate rows because they were built at different times, not because they needed to be separate. Consolidating them into one row recovered ~60px of vertical space. Domain tag: [WC3]

2. **The wc2 floating palette pattern was a constraint workaround, not a design choice** — in wc2, Java Swing couldn't collapse/hide panels, so the floating palette was the only option. In wc3 with collapsible divs and CSS custom properties, the same information fits inline without floating chrome. Don't copy wc2 patterns — understand what constraint they solved and check if wc3 has a better mechanism. Domain tag: [Cross-domain]

3. **Naming zones creates shared vocabulary** — calling it "the admin workbench" vs "databrowser" vs "the right panel" caused confusion. Formalizing TopBar/NavBar/db/db.list/db.detail and adding Shift+hover tooltips means Bill and Claude and any future user can point at the same thing with the same word. Domain tag: [WC3]

4. **Prefs-driven personalization is the path to multi-role support** — `contact.prefs.nav.models` means sales sees Contact/Customer/Order while production sees WorkOrder/Item/Serial. Same code, different experience. This pattern (`contact.prefs.*`) should extend to every user-facing preference. Domain tag: [WC3]

## Scars

- The DetailReview.tsx build breaker existed because 49 detail pages were deleted in a prior session but the review tool referencing them wasn't removed. **Cost:** blocked the app from loading entirely. **Lesson:** when deleting files, grep for all imports immediately — don't leave orphan references for the next session to find.
- The sidebar width was hardcoded as 290/90 in PrivateRoute but the actual sidebar was 200/52 in AppSidebar. **Cost:** persistent left gap that was invisible because both values seemed intentional. **Lesson:** never hardcode dimensions in two places — use a shared constant or read from the same source.
