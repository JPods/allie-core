# Retrospection — 2026-08-07

## What Was Done

Built the Parade of Reports — an Alice-driven onboarding tool that walks new WC3 users through their reports with polished sample data.

### Key deliverables:
- 8 base sample data JSON files covering all major business models (invoice, order, purchase, payment, proposal, statement, contact, item)
- `seed_parade_data` management command that customizes sample data for each of 219 reports and stores it on `Report.config.sample_data`
- `parade-preview` endpoint — lightweight HTML renderer that renders `config.form` layouts with sample data, no WeasyPrint needed
- Preview pane in ReportsDialog — click a print report, see it rendered with sample data on the right half of the widened dialog
- Parade as a Report record (id=319, `output_type=screen`) — lives in the databrowser like any other report
- `output_type=screen` — new reusable report type that navigates to `config.screen_url`
- ParadeOfReports React component with full selection/parade/summary flow and Keep/Modify/Don't Need feedback

### Architecture decision:
Sample data lives on the Report record (`config.sample_data`), not in separate files or a separate model. Each report carries its own customized data — credit memos have negative amounts, pick tickets have bin locations and no prices, RFQs strip pricing, embroidery worksheets have logo specs. The base JSON files are seeder templates, not runtime sources.

## Lessons for Allie

1. **Store data on the record that uses it** — `Report.config.sample_data` not a folder of JSON files. The record carries everything. No lookups, no file-to-record mapping. Travels with WC_HQ sync naturally. The folder files are seeder templates only. [WC3]

2. **Bypass heavy dependencies for previews** — WeasyPrint was broken and unnecessary for the preview use case. A lightweight HTML renderer from `config.form` is faster, simpler, and runs in the browser natively. Save WeasyPrint for actual PDF generation. [WC3]

3. **Features are records, not buttons** — Bill corrected the initial design where the Parade was a button in the ReportsDialog footer. The Parade is a Report record. Users find it in the databrowser like everything else. This is the Data-Driven UI principle applied: the tool IS a record. [WC3]

4. **Per-report sample customization matters** — A credit memo with positive amounts teaches nothing. A pick ticket with prices confuses. A packing slip with cost data is wrong. Each report's sample data must be tuned to show that report's specific features. The `_customize_for_report` function in the seeder handles 30+ variants. [WC3]

## Scars

- WeasyPrint report endpoint broken (`'Request' object has no attribute '_body'`) — discovered during testing, not caused by our changes. Bypassed with parade-preview endpoint but the PDF rendering path needs investigation.

Everything else comes back from library on demand.

## Lessons for Allie

1. **Settings are not a general-purpose store** — alice_pending (70 task descriptions) and alice_log (29 notes) were junk in Settings. Settings carry config that affects runtime behavior. Tasks belong in Action records. Logs belong in logs. This cost 99 records of startup cache bloat. [WC3]

2. **post_migrate fires per-app, not once** — the cache population was running 20+ times at startup because it listened to post_migrate without checking `sender.label`. Gate on `sender.label == 'core'` to fire once. [WC3]

3. **Proxy pattern for library checkout** — Mac calls local Django → local Django proxies to Andi using Connection config (endpoint + key) → Andi returns catalog → Mac displays. React never calls Andi directly. The Connection record is the source of truth for the remote URL. [WC3]

4. **Purpose vs Category** — Category is the menu grouping (form, report, statement, list). Purpose is what the record functionally IS (form-detail, print, export, query). They're orthogonal. A Statement is `category=statement, purpose=print`. A Customer Form is `category=form, purpose=form-detail`. [WC3]

## Scars

- `api_response(error='string', code=400)` doesn't work — `error` must be a dict `{'code': '...', 'details': '...'}` and the param is `status_code` not `code`. Cost a 500 in the browser that looked like an Andi connection failure. Always check function signatures before using them.
