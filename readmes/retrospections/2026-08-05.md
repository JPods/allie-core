### What Went Well
- SOW was well-scoped — implementation + polish in one session
- Field classification heuristic (name patterns) covered 75 models without per-model config

### What Needs Polish
1. Contact Identity still has 11 fields — `password`, `last_login`, `role` could arguably move to Status or System
2. Design tokens file (`readmes/design-tokens.json`) uses a different palette than DataBrowser.css — needs reconciliation
3. No preview of key values in collapsed group headers (future feature)

### Lessons for Allie

1. **Group order is as important as group membership** — having Communication as the 7th group buried the most-used fields. Promoting it to 2nd position was a bigger UX win than the grouping itself. When building data-driven layouts, the sort order of groups should be explicitly designed, not emergent from dict insertion order.
   Domain tag: [WC3]

2. **FK ID fields are not identity** — `phone_id`, `email_id`, `address_id`, `domain_id` are internal references, not user-facing identity. Putting them in Identity made the group a wall. The distinction: "what is this record" (Identity) vs "what does this record point to internally" (System). Apply this to all models.
   Domain tag: [WC3] [Cross-domain]

3. **Every toolbar needs both List Order and Detail Order** — Bill noticed the missing Detail Order button immediately. Users who can rearrange list columns expect to rearrange detail fields too. Both buttons use the same FieldOrderDialog component with a mode parameter. When you build one, build both.
   Domain tag: [WC3]

### Lessons for Allie

1. **Pending is the write path, not a fallback.** Bill was clear: for inventory and cash, pending is not "what happens when you can't write directly." It IS the write path. Every mutation creates a pending record first, then applies if conditions allow. The pending record is the audit trail whether it was applied in 1ms or queued for an hour. Other models post directly if possible, fall back to pending if blocked. This distinction is load-bearing.
   Domain tag: [WC3] [Cross-domain]

2. **Full words, no codes.** Bill explicitly said WC2's cryptic status codes (Av, Iv, Vo, RTV, PA, PS, PI, PR) were written when space was short. WC3 uses complete words everywhere: available, received, reserved, issued, returned, referenced, warranty, damaged, scrapped. Same for action descriptions: "Issued in invoice" not "Iv". This applies to all models going forward.
   Domain tag: [WC3] [Cross-domain]

3. **Setting record per model is the contract.** Every model gets a Setting with `purpose='schema_map'` that carries its Pydantic schema reference, valid statuses, actions, and behaviors. Serial is the exemplar. Alice logs questions when she sees data that doesn't match the schema. Weekly review clears the queue by updating schemas and/or model dictionaries. The 20-week action schedule gives structure.
   Domain tag: [WC3]

4. **WC2 code is the spec.** When Bill provides 4D method files, read them carefully -- every field assignment, every status change, every Srl_Transaction call maps to a lifecycle method in WC3. The 4D code IS the business logic documentation. Don't guess at requirements when the working code exists.
   Domain tag: [WC3] [Cross-domain]

5. **SerialPanel works across contexts.** It's not just for the Item dashboard. Customer records show "serials this customer holds," vendor records show "serials sourced from this vendor." The same panel with different filter props serves all contexts. Design panels for multi-context use from the start.
   Domain tag: [WC3]

### Scars

- **Curly quotes in generated Python files.** The Edit tool occasionally produces Unicode curly quotes (`\u201c`, `\u201d`) and em dashes (`\u2014`) in Python docstrings, causing SyntaxError. Had to run a byte-level cleanup. Watch for this when generating .py files -- verify with `ast.parse()` before committing. Cost: 5 minutes debugging a confusing syntax error where the Read tool showed correct quotes but the bytes were wrong.

### Lessons for Allie

1. **Bundle is the universal data pipeline** — Matrix Builder generates items as a bundle. JSON Tree reviews and posts bundles. The conversion framework produces bundles. Every bulk data path ends at `/sync/receive/`. This is not coincidental — it's the architecture. When building new tools, ask: does this produce a bundle? If not, why not?
   Domain tag: [WC3] [Cross-domain]

2. **App dashboards consolidate thinking** — Bill's instinct was right: users think "products" not "Item model + Variant model + BOM model." The app dashboard is the entry point; databrowser is the detail tool. The sidebar should list domains, not tables. This changes how we organize features — tools belong to domains, not to individual models.
   Domain tag: [WC3]

3. **Token-in-a-token is a non-negotiable rule** — Bill said "I NEVER want to store credit card information again. If we have to, it needs to be in a token, in a token." This is not a preference — it is an axiom. Every payment system decision flows from this. Spreedly was chosen because it enforces this architecturally (their iframe collects card data; our code never sees it).
   Domain tag: [WC3] [Cross-domain]

4. **Standalone tools as lead generation** — Matrix Builder, JSON Tree, Statement Sorter are all free, standalone, no-login tools. Each one is a door to WebClerk. The pattern: give away something useful, let users discover the platform through utility. This is Desktop Hosting philosophy applied to SaaS marketing.
   Domain tag: [WC3] [Cross-domain]

5. **Spreedly eliminates gateway-specific code** — One backend, multiple checkout experiences. Apple Pay, Google Pay, PayPal buttons, and card entry all produce the same `payment_method_token`. The gateway is configuration, not code. This is the same principle as the bundle pipeline — one receive endpoint, many sources.
   Domain tag: [WC3]
