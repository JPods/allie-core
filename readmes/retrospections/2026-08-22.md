All real payment applications use `core.Pending` with `purpose='payment_application'` (13 records in `pending` table vs 1 stale record in `pending_payment_applications`). Removed from `__init__.py` so Django doesn't register it.

- **Signal: update_order_received** — new post_save on Payment. When a payment references an order, updates `order.totals.received` and `order.balance`. Uses `Order.objects.filter().update()` to avoid version conflicts with open browser sessions.

- **Commercial trust principle documented** — negative `available` = customer shortage from prior transaction (they owe us, not we owe them). Example: owed $400, paid $350, available = -$50, liquidated with next $350 payment ($350 + (-$50) = $300 invoice). Retail hides negatives. Commercial shows them because user judgment dominates. ## Lessons for Allie

1. **JSON envelope is the ONLY source of truth** — scalars (total, balance) are denormalized indexes. When they diverge from the JSON, the system shows wrong numbers in toolbars, payment dialogs, and reports. The fix is one compute engine in TransactionBaseModel that syncs both on every save. Never read from scalars when JSON is available. Domain: [WC3]

2. **Negative available is a commercial instrument, not an error** — a customer shortage carried forward. The system must show it so the user can liquidate it with the next payment. Filtering to `> 0` hides real receivables. Alice should learn customer payment patterns and flag breaks from pattern, not flag the flexibility itself. Domain: [WC3] [Cross-domain]

3. **Dead models pollute the resolver** — `PendingPaymentApplication` was registered in Django, intercepting queries meant for `core.Pending`. When two models represent the same concept, one must be removed. Check for this pattern in any model audit. Domain: [WC3]

4. **Conversion should forward context, not auto-apply** — when order becomes invoice, payments follow (invoice_id set, refs updated) but are NOT applied. The user decides when and how cash reduces the receivable. Auto-applying would violate the trust model where trading partners negotiate flexible payment arrangements. Domain: [WC3]

5. **parent_id/parent_model on Payment is origin, not constraint** — tells you where the payment was entered. A customer-level payment is general; an order-level payment is focused but available elsewhere. The origin never changes even when the payment is applied to a different document. This is the same immutability principle as Nora's physical observations — record what happened, don't rewrite history. Domain: [WC3] [Cross-domain]
